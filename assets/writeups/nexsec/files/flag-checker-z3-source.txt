Step 5 — The Z3 grind (a long road of transcription bugs)
Transcribing 60+ constraints from the decompiler output by eye is error-prone. The tricky part is
SSA variable tracking. Ghidra's decompiler emits local_b8, local_c8, R13, etc., and the same
slot is written many times with different byte values across the function. Getting one wrong
makes the constraint set UNSAT.

The bugs I hit, in order:




The root cause for four of them: R13D gets reloaded eight times in the function (c[0x15] →
c[0x16] → c[0x25] → c[0x1e] → c[2] → c[9] → c[0x25] → c[3]). I kept reading it as the initial
value in constraints after 0x037e, where it had been reloaded to c[3].

The debugging technique that finally worked: instead of running the full solve (which only says
"UNSAT"), test each constraint individually against the alphabet domain first — every single one
should be SAT on its own. Then test them cumulatively, adding one at a time. The first
constraint that breaks the cumulative solve is the one with the bug. This localizes the error to a
single line instead of a needle in a haystack.
​
Also worth noting: all four c[3]-bugs were R13-confusion on constraints where c[3] wasn't
obviously a candidate — the "correct" reading looks wrong at a glance, because the flag chars
are all printable and c[3] (index 3 of the flag, which would be s in nexsec26{...}) is a plausible
byte in many arithmetic products.
